# Chen author snapshots: 2018 row linkage screen

The author-maintained [CNNForecasting repository](https://github.com/yahoochen97/CNNForecasting) contains distinct historical candidate-row datasets. This packet screens two versions of its 2018 data against the 288 2018 training-poll rows in the existing 2020-fold preparation:

`python3 research/improvement-loop-20261024/m01-chen-archive-root-v1/compare_2018.py` verifies source bytes and reproduces `2018-candidate-screen.json`. It matches only coarse year, state prefix, signed days-to-election and normalized pollster, then screens for exact Democratic and Republican support values on two source candidate rows with the same source sample size. This is **not** a verified same-poll identity or a fully normalized reconstruction: the source has no unique sample/question ID, and the candidate names, date conventions, populations, source transformations and original releases require independent verification. In particular, the author's inspected later data-generation script calculates `daysLeft` from a range beginning at the field start, while the prepared Tierney file treats its date as a field-end proxy; equality or disagreement between these values alone does not establish poll identity. The script does not establish the transformation used for every older snapshot. Eight 2021-source candidate rows with positive `daysLeft` are conservatively excluded from this screen; no assertion is made that they are erroneous or unusable for a separately specified runoff.

Against the 2019 snapshot, 8 prepared rows have a matching coarse key, of which 2 have one matching support-pair candidate. Against the 2021 snapshot, all 288 prepared rows have matching coarse keys and one-pair candidates. The later count is consistent with a closer data transformation, but does not authenticate the 2023 Tierney source or prove physical respondent/sample identity. The screen requires the two author-source candidate rows to have equal source sample sizes; it does **not** require that value to equal Tierney's prepared `reported_n`. For the 2021 candidate links the two happen to agree on 281 of 288; seven differ. Those differences matter because the Tierney field is defined as the sum of author-derived D/R values and should not automatically be treated as the original respondent N.

The 2019 commit metadata predates the 2020 election, while the 2021 commit is after it and cannot establish the 2020 forecast-time availability of those later bytes. A Git timestamp and present-day public file access are not an independent contemporaneous retrieval log. Previous 2018 outcomes embedded in these files are earlier training information for a 2020 forecast only when their availability is established; target-election results cannot become features. These are revisitable research replays, not sealed holdouts. One researcher saw the first two 2018 outcome fields while examining the 2019 file; no 2020 target outcome was read or modeled by this screen.

The separate [2020-10-12 Chen snapshot](https://github.com/yahoochen97/CNNForecasting/blob/0b63a81a5f89f2373966dc9b35e0faa337aa4ae1/data/CNNdata1992-2016.csv) has the AZ 2012 Rasmussen candidate values 220/250 and source N=500; Tierney has 220/250 and a prepared two-party N=470. The independent `sol-source-review-v1.json` identifies this as a strong, unverified lineage candidate, not proof of a shared physical sample or exact transformation.

File metadata from the GitHub contents API is preserved with Git blob IDs. The repository README states MIT, but no root LICENSE file was found in the inspected tree and reuse rights for embedded third-party polling records were not resolved. The source CSVs are retained locally under `raw/` and are **not** committed to the public research branch; URLs, hashes, scripts and aggregate findings are preserved. No source was admitted, no model was fitted, and no forecast or evaluation changed.
