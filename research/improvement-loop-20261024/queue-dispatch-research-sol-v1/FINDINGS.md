# Independent-job dispatch research V1

This fresh opt-in research layer goes beyond the V2 admission prototype: it launches tiny real subprocesses through the existing `execution.py`, preserves a durable capacity-one reservation across caller death, and reconciles authenticated terminal/cleanup evidence before releasing capacity. It is **not a production controller, DAG dispatcher, migration, scientific comparison, or thousand-cycle adaptive demonstration**. Existing queue code, both admission prototype versions, stores and owner jobs remain unchanged.

## Supported boundary

`dispatch.initialize(fresh_root)` creates a new dedicated domain, V2 admission database, immutable-through-API reservation/release tables and a source-pinned `IndependentDispatchResearchV1` config. The existing root must not already exist. Bootstrap interruption leaves a partial domain for investigation; there is no automatic repair. Capacity is fixed at one and concerns this domain's cooperating dispatch calls only. Direct calls into its executor substore or V2 database bypass this API and are unsupported.

`enqueue(root, plan, expected_sha256)` holds one domain-wide flock around original V2 admission. It accepts only independent jobs: dependency lists must be empty and `resume_prelaunch` must be null. It does not adopt old queue receipts, attempt stores or resumption proofs. Existing V2 ownership/canonical-path rules and fresh plan/executable/input validation apply. As in V2, exact admission retry after an output directory exists can fail its fresh-output admission check; dispatch continuation uses the committed admission directly and does not readmit it.

`tick(root)` holds the same flock across selection, reservation, existing executor operations and reconciliation. When idle it selects one unreserved indexed owner. The selected canonical admission body and digest, queue identity, job/attempt/output ownership, current plan validation, all declared executable/input pins and any retry predecessor terminal/recovery pin are synchronously checked. The output path must still resolve to its admitted canonical absolute identity. Source pins include this module, V2 admission core and the existing queue/executor dependencies. A source change blocks the operation; no updated code is silently adopted.

The reservation stores the entire frozen selected job and admission digest. It commits with FULL-synchronized SQLite before executor preparation. On each active reconciliation the reservation digest/body and exact equality to the freshly authenticated admission are required. Existing executor `load(..., verify_inputs=True)`, registered preparation/output/job-lock claims, exact reserved execution spec, inspect, native receipt pins and output role/minimum-size gates supply the process and output checks. No alternate subprocess lifecycle is invented.

A reservation without an executor directory may prepare. An existing exact, registered, completely unused preparation may launch if no launch intent exists; this continues the **same durable reservation**, not a new resumption admission. A partial/unregistered scaffold stays retained. An attempt already present before reservation is rejected rather than adopted. A launch intent is never automatically relaunched: missing terminal/live/orphan state remains retained. The scheduler does not call stop or recover.

Release requires a terminal validated by the existing executor, verified cleanup, no held job lock, no live recorded process, no owned session members, and known return code. Unknown exit remains reserved even after explicit executor recovery proves cleanup. Known nonzero/timeout/native-output failure can release with its distinct failure outcome; successful execution additionally checks declared receipt roles. An output-gate integrity failure is conservatively retained. The terminal pin, selected output pins, reservation digest, outcome and `unassessed` qualification form one immutable result/release record. One SQLite transaction commits that record: there is no separately published result-before-release window. A crash before release COMMIT rolls back and the next tick re-derives executor cleanup/outcome; a lost reply after COMMIT cannot create another reservation or launch for that attempt.

A retry after a known failure requires a new admitted attempt/output, unchanged logical executor job identity, exact previous terminal/recovery pin and explicit reason. The existing executor checks the retained job claim lineage. This supplies no scientific retry approval. The tests use invented process failures only.

## Trust and integrity timing

Operational observation explicitly says `trusted_mutable_index_no_historical_audit`. SQLite evidence/index bytes, source/config files and cooperating local writers are trusted. SQL triggers prevent updates/deletes through ordinary SQL while installed; filesystem owners can drop triggers, replace the database, forge a consistent state or roll it back. Current active record digests detect incoherent corruption and current external execution/input bytes are checked synchronously. Consistent malicious database rewrite/rollback is not authenticated. The source-pinned config itself has no independently protected external anchor.

Released historical records and their external receipt bytes are not rechecked at every tick. Thus changing or forging a trusted release row can invalidate capacity history outside this narrow storage contract; the current queue's immediate historical-tamper detection is not preserved or claimed. The original V2 structural audit covers admission ownership only; no dispatch-wide audit or protected historical head is implemented here. A SQLite hash/digest is not a stronger immutable-storage boundary.

The original executor's Linux process identity, pidfd, cooperating flock, process-session and local-filesystem semantics remain the boundary. Post-validation filesystem mutation and aliases/bind mounts retain the V2 limitations. Capacity does not cover unsupported external launchers or unrelated stores. Current selected-plan validation may inspect sibling jobs in that same plan, so this is not a constant-cost DAG/frontier implementation. SQLite pending selection and active joins also lack a measured scale claim.

## Reproduction and observed evidence

From this directory:

```sh
nice -n 15 python3 -B -m unittest test_dispatch -v
```

All execution fixtures, source/input edits, intentional integrity corruptions and attempt recovery occur under temporary directories. No scientific model runs. The tests use the existing executor's actual detached supervisors and tiny Python fixture commands. Caller-death probes use separate processes and `os._exit(73)` after reservation commit, preparation, launch, release INSERT before COMMIT, and release COMMIT. Tests check return/cleanup, failed-process retry with pinned predecessor, source/input/reservation/specification/terminal drift, retained partial preparation, unverified cleanup, capacity retention, rejection of dependencies/old domains, and unknown exit after killing a real supervisor followed by explicit existing executor stop/recover. The stop/recover operations occur only in the synthetic test, never in dispatcher code. See `tests.log` for final exact test results; `evidence.json` pins sources and outputs.

The first six-test run passed in 8.115 seconds; the final run adds explicit input/reservation corruption, predecessor-terminal drift, and capacity/unverified-cleanup checks. Two intermediate failures are preserved: `tests-fixed-sleep-failure.log` exposed tests reading terminal files after an insufficient fixed delay; `tests-pre-gate-kill-failure.log` exposed the unknown-exit test killing a supervisor before its child passed the executor gate, so explicit stop correctly refused unresolved ownership. Tests now wait for observed terminal/cleanup and for the real child receipt before the corresponding actions. No executor gate was bypassed or weakened. These are bounded crash-boundary tests, not arbitrary kernel/fsync fault injection or power-loss proof. The unknown-exit test intentionally keeps the reservation; temporary fixture cleanup occurs after assertions.

## Concrete remaining work

Dependency materialization/authorization, authenticated cross-plan producer result/release/terminal/output chains, runnable frontier bookkeeping and real DAG execution remain absent. Independent-job input pins may refer to supplied files, but this API does not establish an authorized producer chain for them and rejects dependency declarations. There is no full dispatch audit, protected store anchor, robust bootstrap repair, explicit reservation cancellation, prelaunch deferral release/resumption lineage, controller work loop/service, portable restore, production migration, comprehensive concurrent-dispatch crash campaign, or independent review acceptance. Unknown/orphan/corrupt reservations intentionally require investigation and can block this capacity-one domain forever. These are precise gaps rather than simulated success.
