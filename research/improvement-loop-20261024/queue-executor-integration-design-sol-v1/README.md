This packet only reads, hashes and parses source; it runs no fixture, executor, graph, fit or owner job. ## Two concrete compatibility risks

1. **Historical-input policy conflict.** E:345–354 `ownership_intents()` calls `validate(spec)` on every historical intent. E:124–166 validation rechecks executable, cwd, input/source pins and canonical output namespace. Q's inherited test `test_prepared_input_drift_defers_without_terminal_and_unrelated_job_runs` (test file:496–519) deliberately drifts an old first job's input while an unrelated job uses an independent unchanged source. Original behavior defers the first job and runs the unrelated job. A direct replacement would reject that unrelated job's preparation at E:396 while scanning the old intent. Q:544–552 could then record another prelaunch integrity deferral. This is a source-derived predicted regression; it was **not** executed here.

   Before implementation, specify ownership-registry structural validation separately from fresh runnable-input validation. Preserve exact historical intent bytes, canonical declared identities, source/store/lock/claim fingerprints and containment conflict detection. For admission/launch of the target attempt, preserve all fresh input/executable/cwd validation. A moved output symlink or changed historical input must still be visible in the appropriate audit and may block affected dependencies or final qualification; it must not silently disappear. Do not merely delete `validate()` and assume equivalent guarantees. If the intended policy instead globally quarantines all historical drift, explicitly version that semantic change and revise the prior unrelated-work guarantee rather than claiming all old behavior preserved. The requested compatibility-preserving design needs this distinction independently reviewed.

2. **Released jobs bypass new registry checks.** Q:274–320 `verified_result()` authenticates result/release/terminal/output bindings but never calls new E.load/registered/ownership validation. Q:476–485 takes that path for released reservations and continues; finalization calls this tick (Q:623–630). E.load now checks the new ownership store and ownership-intent pin, but that alone does not make Q recheck those artifacts after release. Replacing E alone therefore does not automatically detect later missing/drifted ownership metadata during queue finalization.

   Add a reviewed **read-only ownership audit** at queue reconciliation/finalization, under the ownership lock, using the structural/history distinction above. Authenticate exact store, intent, prepared, job and output claims and attempt roster against the queue's bound effective specs; reject unknown/external attempts in the dedicated managed domain. Include those exact evidence pins in F.evidence (currently F:61–74). For result paths with terminals, preserve original terminal/output/dependency checks as well. Empty/dependency-blocked runs may never initialize an execution store: absence is acceptable only when the accepted execution/reservation roster proves no preparation occurred; disappearance of a previously witnessed store must fail closed. Audit receipts must not claim a guarantee beyond the source-bound evidence actually checked.

The current queue's capacity contract requires **all managed-domain launches through its dispatcher**. New ownership locking does not let direct clients bypass queue reservation accounting. The queue and ownership locks protect different invariants.

## Lock order and transaction boundaries

Names: D = queue dispatcher flock; S = intake SQLite BEGIN IMMEDIATE; O = executor ownership flock; J = original per-job nonblocking flock inherited by workers.

| Operation | Acquisition and release order |
|---|---|
| Enqueue/seal | D → S for canonical intent/seal commit; enqueue original read-only preflight may inspect J nonblocking. Commit/close S before real file admission; later D → S records ACCEPTED. D covers the whole operation. |
| Tick preparation | D → O → J(nonblocking). O and manager copy of J close before launch; D remains. Complete exact replay may not acquire J. |
| Launch | D → J(nonblocking), then worker inherits J. Manager closes its copy without LOCK_UN. No ownership lock inherited by worker. |
| Worker/stop/recover | Worker may hold J and read source/ownership bindings; current E.load does not acquire O or D. Stop/recover take or prove original J/process identity boundaries. They must not enter D while holding J. |
| Proposed ownership audit | D → O, read/verify immutable evidence, release O; then finalize D → S commit, close S, fsynced projection under D. No waiting for workers while holding S/O. |

No existing E path acquires D. Preserve this absence; do not add a callback from E.prepare to queue enqueue/seal/finalize while O/J is held. Do not wrap every E.load with a blocking O acquisition: supervisor/child paths call load while inheriting J, and that changes latency/liveness assumptions. O must not be held while waiting for child completion, acquiring D, or doing SQLite work. J remains nonblocking; a live job is observed/reserved rather than awaited under D/O. A source-level order argument excludes the obvious lock inversion; it is not a runtime deadlock or bounded-wait proof. O's blocking flock can still stall D behind a stuck cooperating preparer/fsync; bounded lock acquisition/backoff would need a separate reviewed policy and tests.

There is no single atomic transaction across SQLite and executor files. Keep the current write-ahead order: accepted queue intent → pinned queue binding/reservation → fsynced executor ownership intent → exact prepared scaffold/job claim → queue dispatch intent → executor launch intent → observed terminal → queue result/release → SEALED+reconciled final DB bytes → final projection. Each transition requires its existing replay/authentication rule. Never use one system's incomplete receipt as proof the other committed.

Retain all stated filesystem/fsync/owner-writable evidence assumptions. External deletion of the sole executor intent before any other witness is a known negative boundary; the queue's independently committed accepted plan/binding/reservation can supply another local witness only if the new audit actually cross-checks it. No implementation or equivalence claim follows from this design.
