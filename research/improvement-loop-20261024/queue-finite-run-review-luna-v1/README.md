# Independent review: finite-run queue integration V1

The bounded integration tests pass, and source inspection supports the central finite-intake design: V3 enqueue/tick paths execute under the same dispatcher lock, SQLite transactions sit inside that lock, durable `ADMITTING` claims precede scaffolding, and exact retry repairs interrupted admission even after seal. Sealed pending admissions block all dispatch. Finalization invokes original reconciliation under lock and requires terminal, dependency/release, reservation and quarantine conditions before committing final bytes. The selected real-executor tests passed in my rerun: 20 tests total in 9.854 seconds. Empty and failure outcomes remain separate from scientific qualification.

I found an inherited output ownership gap. I reproduced that both V3 and the finite-run successor accept output root `/shared-output` and another unrelated plan's output root `/shared-output/data.txt`, before either exists. The existing fixture writer uses `data.txt` as a file under its output root, while the second job requires that same pathname as a directory. No overlapping jobs were launched. The same flaw is present among crash-left `ADMITTING` claims because they are compared only by exact string. The executor's global output claim also hashes exact path strings.

A correct ownership rule should reject canonical path component-prefix overlap within a plan and across accepted and `ADMITTING` claims while holding the dispatcher lock, and should extend to direct executor calls if those are supported. This is inherited from V3 and should be tracked separately from lifecycle correctness. Exact reproducer scripts and stdout are preserved here.

The integration is still a bounded research successor: it uses a new store schema, the original full regression suite was not run, power-loss durability and scale are unproven, and no scientific job or owner store was touched. Full pins and evidence are in `review.json`.
