# Same-operation ownership audit elision: counterexamples and narrower next step

No full-result ownership cache is implemented or admitted. The existing dispatcherD lock does not establish that an ownership_audit result stays valid through a single operation. Four focused tests use4fresh histories with actual tiny accepted executor jobs under unchanged ancestor queue source in temporary scratch; no fabricated historical SQL/files or model work. They pass in2.47s. Source pins and prior artifacts remain unchanged. This finding rules out lock-only/full-snapshot reuse, not all possible carefully guarded structural optimization.

## Concrete deterministic counterexamples

1. Keep exact dispatcher flock continuously held, audit successfully, then change a released job's external input bytes while preserving byte length and restoring originalmtime. Next true audit has nonempty historical_input_drift while ownership evidence pins are IDENTICAL to the first audit. Cached success/drift would silently misreport freshness even with expected spec/source namespace pins unchanged. This is a descriptive historical drift check, not proof an unrelated job must be globally blocked; the current source deliberately permits unrelated progress.
2. KeepD held, replace an empty job-lock file with identical bytes but a different inode, keeping original inode separately for restoration. Next audit rejects job lock identity changed. Namespace content digests alone do not cover registered()'s device/inode condition. The old success snapshot would accept a condition current source rejects.
3. KeepD held, corrupt an ownership jobclaim. Next audit rejects. A cooperating manager normally cannot do this whileD is held, butD does not prevent user/raw-file edits or same-operation internal partial publication. Cache assumptions cannot silently erase the current fail-closed check.
4. A separate cooperating manager trying status on the same fresh store times out onD, as intended. This confirms whatD protects: cooperating dispatcher entry, not external input contents. It does not prove arbitrary actors honor the lock or establish input/namespace immutability.

All mutations are in disposable review-owned stores and restored. No runtime cache was added, no frozen store was adopted by a different version and no owner job was touched. Baseline partial-prepare crash paths remain in the existing reviewed implementation; no new cache crash/replay behavior is claimed tested.

## Exact source checks that an operation lock cannot replace

execution.py ownership_audit still calls assert_manager/domain/source checks, bounded ownershipO acquisition, ownership_intents roster/claim validation, expected effective-spec/required-state checks, per-attempt prepared/specification/current claim pins, registered() including job-lock inode, and validate(spec) for EVERY historical intent. The latter resolves current paths/executable/input pins and refreshes live drift. Terminal/output/process/session/dependency/recovery checks elsewhere are separately live. Note the original design's path-order wording was corrected in the separately pinned addendum: intent comparison has lexical validation first, live resolve validation later in audit.

Within _tick_locked the manager itself can publish reservation/binding/ownershipack/dispatchintent and call prepare, which may create durable partial state then raise or crash. A cache key only(root, PID, heldlock, expectedmapping) does not encode every current condition; closing/reopeningD can reuse numericFD/inode/process identity. A crash destroys in-memory scope and any recovered operation must start fresh. No persistent cache/old operation token is defensible from these observations.

## Safer structural design, still not a shipped bypass

A future separately reviewed scope must be created only after exact managedD acquisition, with a unique operation nonce and finally invalidation beforeD closes. It cannot span status→tick→finalize or process/restart. Invalidate BEFORE prepare and in finally even on failed/partial preparation; same for any structural publication/repair. Freshly derive expectedmapping everyuse; requiredflags change with ownershipack/dispatch/launchintent. Keep boundedO acquisition percall; do not holdO acrossprepare/workerwait (lock order/deadlock/latency would change).

Before structural reuse, re-enumerate full intent/attempt/output/jobclaim topology, read/hash all relevant currentbytes including optionalfile presence, validate source/domain/store and job-lock device/inode. Unknown/missed topology is an uncached full-audit miss. Re-run every livevalidate(spec) on every invocation, never memoize historical drift or artifact/process/dependency qualification. Return deep copies, preserve error classification/evidence roster, keep final uncached audit initially. Current frozen source has no complete mutation-epoch or snapshot-guard interface; implementing an incomplete one would be a weaker representation. This packet therefore stops at tested counterexamples and concrete guarded design rather than claiming safe audit elision.

Such a design may save decoding/logical reconstruction but still scans/rehashes history. It does not remove repeated O(history) hashing peraudit or aggregate quadratic repeatedhash work. Cooperating writers withD excluded are only one part of the trust envelope; externalinputs remain mutable. Arbitrary hostile filesystem changes and atomic snapshot guarantees are not solved by either current or proposed source. A no-change observation between two samples is not proof of immutability.

## Measured narrow optimization opportunity

One additional REAL tiny accepted job, followed by2unchanged full audits under continuousD, was instrumented WITHOUT caching/skipping checks. execution.decode was called46times on7distinct exact byte/type inputs:39repeat decodes,35520total decode-input bytes. execution.pin was called58times, reporting16464820bytes including repeats. These count only the wrapped execution functions, NOT all reads/hashes/syscalls/CPU; no throughput or scaling conclusion follows.

A bounded pure-decode memo is the cheapest next experiment: key by full exact bytes AND inputtype plus fixed decoder implementation, cache only successful JSON decoding, return deepcopies to avoid caller mutation, preserve duplicate-key/nonfinite/invalid error behavior, cap entry/rawbyte budget and bypass largeitems. Every existing read/hash/namespace/lock/live validation must remain; this memo does not need or imply authority to reuse an audit result. Benchmark with meaningful actual tiny histories and mutation/error differential tests before claiming a speedup; deepcopy/storage overhead may offset saved parsing. The observed39duplicate parses show an optimization target, not demonstrated benefit, and the much larger pin-byte count shows the rehash problem remains.
