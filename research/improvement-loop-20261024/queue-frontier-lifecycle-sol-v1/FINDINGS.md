Descendant lifecycle research: new isolated queue domain

This derivative addresses two explicit gaps in queue-durable-frontier-sol-v1: failed grandchildren previously stayed waiting indefinitely, and no completion semantics existed. The frozen predecessor and its independent review are preserved. This is still research under the trusted mutable SQLite/cooperating-writer boundary, not a production queue or service. No model runs, owner queue operations, scientific promotions or production migrations occurred.

Implemented transitions

A fresh configuration and database schema version reject the prior admission/dispatch domains. Immutable owner claims, canonical admission evidence, dependency edges, capacity-one active slot, partial runnable index, executor integration and selected dependency reauthentication are inherited. Source verification still checks actual loaded V2 validator/admission origins and source roster before lock creation. Counter/meta changes happen only inside existing BEGIN IMMEDIATE transactions.

blocked_terminal contains one immutable record per never-executed descendant, with a foreign key to the failed producer's committed release, complete root release-record digest and an explicit transitive_failed_dependency reason/science-unassessed label. On a failed producer release, a recursive SQLite UNION computes the descendant closure, deduplicating diamond paths. Every newly blocked descendant must still be pending, never reserved/executed; otherwise the release fails closed and retains capacity. The transition inserts causal blocked records and removes all affected pending rows. Already blocked descendants retain their first valid cause and are neither relabeled nor recounted if another ancestor fails. The first cause is sufficient to explain blocking; this is not a ledger of every later failed ancestor.

Immutable release insertion, all new blocked records, pending removals, active-slot deletion and lifecycle counter updates commit together. Crash before commit rolls back the entire failure closure and release; the producer remains active for exact replay. Crash after commit retains the whole closure and release. The same immutable release/active ownership gates prevent a repeated committed failure decrement. A second independent failed root may revisit the shared graph, but does not repeat logical blocking mutations. No postcommit repair/replay queue is required for these authorized transitions because there is no separately committed propagation window.

Successful releases preserve the prior direct producer-count update, ignoring consumers already terminal-blocked. Unknown process exit, live processes or unverified cleanup do not release, propagate failure or claim completion: active capacity stays occupied and downstream jobs stay unauthorized. Complete selected producer/result/release/terminal/output/executor checks remain synchronous before launch, including the after-prepare recheck. The frontier and counters do not authorize execution themselves.

Lifecycle/completion meaning

One fixed counter row records total admitted jobs, pending, active, released executions, terminal-blocked, accepted executions and failed executions. SQL CHECK constraints enforce nonnegative counts, active<=1, total=pending+active+released+blocked and released=accepted+failed. Admission, reservation and release update counts within the same transaction as their projections. Completion reads the fixed row plus at-most-one active slot and bounded existence probes of pending/blocked rows; it never counts all historical owners/releases. Presence mismatches fail closed, including a balanced-looking zero-pending counter while a pending row exists.

A snapshot distinguishes empty, active, runnable, waiting_unresolved_not_complete, all_terminal_with_failures_or_blocks, and all_terminal_execution_success_unqualified. all_terminal means no currently admitted pending or active job: every admitted owner is executed-terminal or terminal-blocked under authorized transitions. An empty store is vacuously terminal but all_executions_accepted_unqualified=false. Failure/blocked completion is never reported as success. Even all accepted executions remain scientifically unqualified. A new admission atomically increments total/pending and reopens the snapshot; this is not an admission seal, promise that no future work will arrive or unattended-service shutdown authority.

Explicit audit_frontier reconstructs immutable ownership/edges from canonical plan evidence, independent failed-root descendant closure, blocked causal rows/digests, pending counts, active partition and exact lifecycle totals. It checks that terminal-blocked and pending partition all never-reserved owners. The audit is deliberately O(history+graph), may repeatedly traverse roots and reads stored result declarations; it is structural rather than full historical external-input/executor authentication. No automatic repair occurs. Completion is an operational projection under trusted mutable storage, not a new full-history audit or protected archive head.

Tests and bounds

Eight final tests passed in4.534seconds (tests-final.log); earlier six/seven-test logs are preserved. Tests execute only invented tiny commands in temporary dedicated roots, at nice15 with thread environment1, CPU soft40/hard45seconds, AS512MiB, file16MiB and outer wall60seconds. Native hold fixture is stopped only through its owned PID/session identities; owner/model jobs are never touched. Suite-wide peak process-tree RSS/transient disk and physical I/O were not separately instrumented, so resource caps and reported elapsed time are the bounded evidence.

Real client processes use os._exit during admission after counts/frontier insertion; reservation before/after commit and prepare/launch; and failure release at release insertion, first descendant insertion, completed closure/counter update, before commit and after commit. Assertions verify active/pending/blocked/count partitions before and after replay. A real two-root branching diamond with a deeper descendant produces four immutable blocked records, never launches them, retains the same causal bodies after the second root fails and remains unchanged on idle replay. This tests logical idempotence, not a claim that recursive traversal costs zero.

Other tests cover a fully successful dependency chain and later admission reopening completion; concurrent admission and two ticks during a producer failure with a separate ready owner; unknown supervisor exit with no false blocking/release/completion; stale unresolved-count corruption that remains waiting rather than complete and is exposed by audit; balanced but false zero-count corruption rejected by bounded presence guards; source/config hash drift before lock creation; and refusal of the prior admission core on this new database domain. No fake successful model or scientific outputs are used. Process death tests cover SQLite rollback-journal/FULL-sync recovery after client termination, not actual OS crash, disk failure or power-loss durability.

Source assumptions challenged

Independent predecessor review found bounded frontier correctness under cooperating writers but explicitly lacked recursive failed lifecycle and completion. This derivative narrows that gap; it does not expand the storage trust claim. Tests demonstrate selected source drift/version refusal and counter inconsistency detection, but they do not make raw SQL a supported writer. A filesystem owner could drop triggers, rewrite release/result facts and coherently rewrite all counters/projections; rollback to a consistent older database or external historical output tamper is not detected by untouched idle rows. The shared executor/current-source modules are source-pinned and unchanged; current file hashes/path checks do not provide a hostile same-user Python-memory or filesystem race sandbox. Source/review drift outside the supported single-version domain remains a manual stop/review condition.

Remaining gaps before adoption

No failed-bootstrap repair, automatic counter/frontier repair, cancellation, manual unblock, same-plan resume, cross-plan dependency contract, store migration, backup/restore anchor, protected immutable history or unattended daemon exists. A blocking job has no fabricated executor result/terminal; future retries must use a separately designed explicit new-attempt policy, not change the immutable blocked row. All-terminal is an instantaneous current-admissions snapshot, not work-intake finality.

Propagation uses one transaction for the full descendant closure: large DAGs can hold the dispatcher lock and use substantial memory/journal space; multiple failing roots can revisit the same closure. No large-DAG, thousands-cycle or authenticated-history scale result is supplied. The predecessor's SQL-selection benchmark cannot be silently reused as a measurement of this new propagation/completion path. Selected full-plan/executable hashing and recursive ancestor authentication remain expensive. Bounded/batched propagation would require a separate crash-safe in-progress/terminal protocol before completion could be asserted; it is not introduced here.

Disk-full/fsync uncertainty, database/OS power loss, graph recursion/resource exhaustion, failed initialization, malicious mutable-store changes and all inherited executor supervisor/process-lifetime caveats remain. A closure failure must leave the active reservation retained, never be treated as completion. Independent review and explicit durable-service/storage/lifecycle requirements are necessary before integration; no production-ready claim follows from these tests.
