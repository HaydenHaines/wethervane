# Independent review: synthetic parent-conditioned kernel reuse

## Verdict

The packet's limited conclusion is sound: a tiny symbolic exposure input can reproduce the same synthetic fixed-parent log density and gradient, and the pinned current component source makes exposure the only direct numerical parent value in this composition. This is useful feasibility evidence for a future generic kernel factory. It is not evidence that the actual TX graph can be replaced safely, that current compiled model callables accept another parent, that the likelihood is normalized for each conditional parent, or that a parent identity/mass is safely bound to each call.

## Source and parent checks

I independently read the pinned `components.py`, `graph.py`, `inputs.py`, `provider.py`, and the saved selection metadata. The selected `ProtectedPopulation.exposure` provider reads `c.protected["exposure"]`; downstream numerical terms consume the typed exposure port through cell intensity and dependent count rates. The other selected component numerical inputs come from the problem/context, not other parent record fields. The compiler's exact-array guard checks that the provider emits a NumPy array equal to the protected exposure before tensor conversion. The compiler later places parent identity, parent ID, upstream identity, and mass in the target/contract metadata, with `parent_mass_used_in_logp=False`; those metadata affect target identity, not the numerical density graph.

I verified the selected eight full parent objects exactly equal the pinned upstream `parents.json` (SHA-256 `587e8cd7786d9c9ed57d588978752e27a4dd829bb03d68b4f3afa17a99026ce9`). I also checked the upstream bank file hash (32,012 bytes, SHA-256 `9db6fd66fa08d2b5353aaddcb468e3ed4b185c021b8eb99be7b42d1ce82d3e10`), `bank-metadata.json` (`b9d39ee42c2c2a0884a566ac4e00da460040df54bbe91122d629c76408156d3f`), `event-projection.json` (`c2fbd3bb4299410b03d54e0f6656945d197100252bf32ac5cad04f3a8d5ae499`), `launch.json` (`e6c1d6f36ff6e8769b1fed69e9671c42c43e50f2dc8980b198b29bcaede74e76`) and upstream receipt (`7c907dfb83e1cb8c33c0241d5a5c117912f2860e7f407c7f213b83651b52cebb`) against the paths/hashes pinned by `selection.json`. No actual model graph or forecast was built/run.

All eight parent records have the same `problem_identity`, `upstream_identity`, event IDs, cell IDs, schema and mass (`0.125`); row IDs and parent IDs differ. Each exposure is a positive finite 3x24 matrix, and exposure differs across parent records. In `inputs.py`, `Parent.identity` hashes canonical JSON for the complete parent record; a mass change changes this identity even when exposure is held fixed. Thus a reusable numeric kernel must receive a whole-parent exposure, and a separate trusted wrapper must bind it to the selected full parent/target envelope. The probe checks only matrix shape and positive finite entries; it does not authenticate event/cell axes, upstream lineage, row ID, parent ID, or mass. Its static masses list is outside the kernel and does not test parent-to-mass association.

The current `compile_model` deliberately rejects a symbolic provider exposure and any different NumPy exposure. That proves the existing API is not a mutable-parent API. The proposed exact-port substitution route is plausible but has not been attempted against the actual graph. Exact node survival in actual pre-optimization logp and gradient graphs, and absence of any other parent-dependent constant in that actual graph, remain open gates.

## Bounded synthetic reproduction

I copied `probe.py` to a fresh `/tmp` directory and ran it with the calibration venv, one-thread settings, a fresh local PyTensor cache, C++ disabled, `nice -n 15`, and `numba__fastmath=False`. The A→B→A results agreed with each fresh fixed-parent model at one six-coordinate point: maximum reported log-density error was `1.78e-15` and maximum gradient error was `4.44e-16`. Wrong shape, nonpositive and nonfinite exposure cases rejected. I appended an independent central finite-difference calculation in a second temporary copy; maximum gradient discrepancy was `3.61e-9` for A and `3.69e-9` for B. These confirm the synthetic graph substitution and its derivative behavior at the tested point; they do not validate the real 662-coordinate graph.

The synthetic gamma coordinate transformation is internally consistent: `log_g = center + scale*t - log(base)` has derivative `d log(g)/dt = scale`; the log-gamma density contribution uses `log_g + log(scale)`, which is the corresponding log-Jacobian. PyMC's logp with `jacobian=True` also includes the LogNormal value-variable transform. Fixed and symbolic graphs are built from the same code, however, so their parity alone would not detect a Jacobian omitted in both. My finite-difference check supports the derivative of the implemented synthetic logp, not the scientific correctness of the actual model's factor inventory.

## Reproduction caveat and limits

The frozen `probe.py` records `pytensor.config.numba__fastmath` but does not assert or set it. My first fresh run without an explicit flag inherited `fastmath=True`; the claimed reproduction configuration is therefore environment-dependent unless the launcher pins/asserts `numba__fastmath=False`. Re-running with the explicit false setting succeeded and matched the packet's reported setting. No conclusion about this run applies to fast-math differences in a full TX compile.

The source audit is path-dependent: it assumes it sits alongside `m01-native-successor-provider-sol-v1`, so copying `source_audit.py` by itself to `/tmp` cannot run. I did not run it against its original output paths. I manually verified the parent source hashes and records described above. The AST check in that script detects direct `c.protected`/`c.parent` attribute expressions in `components.py`; it should not be generalized to future components that alias context values or read parent data through helpers without corresponding source review.

The result supports only a next experiment: build a separate source-bound kernel factory with an explicit exposure input, preserve the original value coordinate order and all factors/Jacobians, and require a wrapper to verify the complete parent record, IDs, axes, lineage, mass and exposure before invocation. Do not change the native compiler guard, mutate a compiled TensorConstant, pool parent conditionals, or claim conditional normalization from these tests. The packet correctly leaves those steps unexecuted.
