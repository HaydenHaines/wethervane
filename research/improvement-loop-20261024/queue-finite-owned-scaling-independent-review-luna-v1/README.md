# Independent review: finite-owned queue scaling design

This is a source-only review of the frozen scaling assessment and its unexecuted benchmark plan. I did not import or run the queue, launch a fixture, inspect current owner jobs, or run a workload benchmark. I ran the design packet’s four arithmetic unit tests; all passed.

The main cost model is correct under its stated healthy same-root assumptions. A plain idle tick revisits each released reservation in reconciliation and again in the status snapshot. Each `verified_result` reaches `ownership_for_job`, which rebuilds the expected roster and runs `ownership_audit`. An audit reads all intents, performs all unordered output-containment comparisons, and live-validates each historical spec (including executable verification). With R reserved results and A intents, the source-derived terms are `R*A*(A-1)` pair comparisons and `2*R*A` executable verifications per idle tick. If R=A=N, this is `N²(N−1)` comparisons and `2N²` rehashes. At N=1000 and the stated 8,020,928-byte interpreter, 16,041,856,000,000 is logical hash input bytes, not device reads or a time prediction. Status and finalization formulas also match the call path, excluding full evidence serialization costs.

The proposed first pilot is cautious and useful for measuring tiny queue overhead: actual source-bound code, fresh temporary stores, one live no-fork job, a hard launch cap, completed-idle-tick measurement, exact roster counts and preserved checks. It is not representative of scientific worker cost, highly contended storage, multiple-root orchestration or thousands of cycles. The plan’s cumulative 1/2/4/8 prefixes should be explicitly identified as one evolving history versus separate cohorts. Scratch outputs must remain outside the frozen packet; the packet correctly identifies that `run_tests.sh` rewrites its cleanup evidence if run in place.

Before execution, operationalize active-owner-load controls. The current plan asks for a fresh resource check but does not specify recording owner job/queue activity, host run queue and pressure, disk latency/free space, cgroup resource counters, or detached worker-tree usage before and during the trial. Nice 15 and controller-only RSS do not isolate shared load. Define what happens if an owner job starts mid-batch, preserve contaminated/partial evidence under predeclared rules, record cache conditions without dropping global caches, and bind a fresh owner-reserve/headroom decision. These are measurement controls, not a reason to run anything now.

No additional complexity-arithmetic defect found. This review is not a performance result or production/scale approval. See `review.json` and `source-pins.json` for exact source hashes and detailed limitations.
