# Correction: audited the wrong frontend subtree in the initial review

## Retraction and corrected scope

The initial `REVIEW.md` incorrectly treated `web/` as the deployed frontend. At the pinned repository HEAD, `package.json` runs the root Next.js app and its `app/page.tsx` renders `components/ChamberExplorer.tsx`. That component selects `HouseWorkspace` for `?chamber=house`, which has current and historical House editions. I retract the initial conclusion that no House presentation exists and the associated claim that current House 0%/100% risk could only be assessed through analogous Senate views. The original file remains unchanged as a historical record; this correction and its pins supersede those claims.

The corrected review below is source-only, pinned to `deploy/siteground` HEAD `317ff150f012871aec6c71ae680d7e76eec5b4db`. It inspects current 2026 House presentation and historical group presentation, not raw prediction arrays. No site files were changed or deployed.

- Root `app/page.tsx:1–5` renders `ChamberExplorer`; `components/ChamberExplorer.tsx:9–16,80–125` routes the `house` query to `HouseWorkspace`. `components/HouseWorkspace.tsx:58–82` chooses current vs historical House editions. `components/HouseLiveWorkspace.tsx:139–148` passes the current view to `HouseLiveResults`.
- The current live result schema has `outcomes` with party/group identities and `p_win`; it allows 1–3 outcome groups (`lib/house-live-result.ts:36–43,150–163`). The view projection transfers the `p_win` value but no explicit race-level `structural` flag, outcome draw count or outcome-specific MCSE (`lib/house-live-view.ts:21–39,76–109`). It does carry a global joint-draw digest/count/chain count/ordered race IDs (`:58–60,138–140`). The live results page reports the global count and aggregate chamber MCSE, while warning that the standard error is finite-simulation variation separate from election uncertainty (`components/HouseLiveResults.tsx:279–280`). It does not show the per-race numerator or per-race precision beside each win chance.
- The existing joint-data checker recomputes each race/group outcome frequency from the same joint rows and compares it to `p_win` (`lib/house-live-joint-check.ts:102–108`). This establishes an internal frequency consistency check, not extra independent draws or a per-race effective sample size. Do not infer a binomial interval or a certainty bound from the row count, or from a weighted effective sample size.

## 0% and 100% display paths

- `lib/presentation.ts:100,109–114` formats ordinary percentages to one decimal. Exact 0 and 1 therefore display `0.0%` and `100.0%`. Values strictly between 0 and .001 show `<0.1%`; values strictly between .999 and 1 show `>99.9%`.
- Current live district detail renders each `p_win` with that helper (`components/HouseLiveResults.tsx:88–99`) but has no endpoint-specific note. The map’s accessible title/label includes the top outcome’s probability (`components/DistrictMap.tsx:250–260`), and the live map legend gives Safe/Likely/Tossup thresholds and says they are model chances, not guarantees (`components/HouseLiveResults.tsx:233–245`). The live ribbon (`components/HouseGroupRibbon.tsx:60–70,74–90`) places all D/R/O values in tile title/ARIA text, but for modeled endpoint values its text does not say “0/N” or warn that no/all saved draws is not impossible/certain. Chamber control similarly formats D/R/unresolved probabilities and bars (`components/HouseLiveResults.tsx:126–146`); its nearby section text explains unresolved status, while the general numerical note is farther below.
- **Concrete support-loss risk in live ribbon adapter:** `components/HouseLiveResults.tsx:153–161` constructs D/R/O probabilities using `?? 0` for any group absent from `race.outcomes` and does not set `structural`. `lib/group-ribbon-layout.ts:4–19,70–89` accepts an optional structural flag and labels false/omitted as modeled. Thus the ribbon turns an absent group into a numerical zero and labels the valid triple as modeled, instead of preserving the distinction between absent from listed outcome support and a supported group with zero observed joint draws. The live schema’s 1–3 outcome allowance makes this a real representational edge, even if the current roster happens to contain all groups in a particular saved result.
- Historical House group details do distinguish these cases: `components/HouseGroupRaceDetails.tsx:54–58,78–82` says a one-group source list is a model rule rather than an election guarantee, and for modeled 0/1 frequencies says no/every saved draw yielded the group but that does not make it impossible/guaranteed. It also states group chances are not vote shares and are not allocated to members (`:59–67`). It does not put the saved-draw denominator beside the endpoint.
- Historical map/ribbon paths maintain unavailable forecasts outside probability ranks (`components/HouseGroupResults.tsx:100–114`, `components/HouseGroupRibbon.tsx:107–114`). A group ribbon majority marker is explicitly a seat-count guide rather than probability the district decides control (`HouseGroupRibbon.tsx:78–86`); for historical results without qualified chamber support, the control/tipping panel is explicitly unavailable (`HouseGroupResults.tsx:111–114`).
- Historical candidate-level `HouseExplorer` includes a finite-simulation endpoint note for its own legacy candidate forecast (`components/HouseExplorer.tsx:675–702`). Do not assume this protects the separate current House or group-result components.

## Corrected recommendation and tests

The current design already has some useful safeguards: one-decimal display avoids turning small positive values into 0%, `<0.1%` / `>99.9%` protects near-endpoint nonzero estimates, map language says chances are not guarantees, and the historical group detail differentiates structural one-group support from finite-simulation endpoints. The remaining presentation gap is strongest in the current live race detail, chamber summary, live ribbon, and accessible map labels.

For a **supported, modeled outcome** at 0 or 1, retain the point estimate but put the finite-draw interpretation adjacent: e.g. “0 of N saved joint draws” / “N of N saved joint draws.” Add “This finite simulation result does not mean impossible/certain.” Use actual counts only if counted from the authenticated ordered joint draws; do not reconstruct numerator by multiplying a rounded `p_win` by N. The fact that all districts share a coherent joint election draw also means those district outcomes are dependent; N is a row count, not a count of independent district-level experiments.

For **structural absence**, do not manufacture `0.0%`; represent the group as absent from the listed support (or an explicit not-supported status). For **one supported group**, say “the only group in the listed support; assigned all group probability under this model rule; not a guarantee.” Keep **unavailable forecast** as its own state. Current live data should carry an explicit outcome-support/probability-method field through `house-live-result` → `house-live-view` → map/ribbon/detail, instead of having the ribbon adapter infer missing groups as zeros. The listed roster itself is not a guarantee that all possible write-ins/opponents were captured.

Recommended regression cases before presentation changes:

1. Current live race and chamber at exact 0/1, near 0/1, and ordinary probabilities; verify the visible text and all `aria-label`/`title` text identify a finite model estimate, with correct numerator/denominator when available.
2. A current race with only one declared group, three supported groups with one group having zero observed joint wins, and a missing/unavailable race; assert each has distinct support semantics and the ribbon does not fill absent groups with a modeled 0.
3. Historical group fixtures for structural support, modeled 0/1 endpoints, and unavailable prediction; keep the current disclosure that endpoint simulation counts are not impossibility/certainty. Check map, ribbon, detail and screen-reader labels, not only detail prose.
4. Validate that probability values, counted joint-row numerator, row denominator and group identity agree with the authenticated draw decoder. Do not add a binomial interval based on N or an effective weighted N; show the declared numerical precision/error method only.
5. Verify three-way chamber percentages preserve D/R/unresolved mass, keep Other seats unassigned as stated, and do not describe the race ribbon/seat-count marker as a tipping probability.
