# Independent review: scoped selection queue

26 October 2026. Reviewed `selection_queue.py`, `selection_queue.md`, `test_selection_queue.py`, the author verification receipt, and the queue, executor, and scoped-selection boundaries they call. This review did not edit implementation, run a native model, enqueue a real job, or write an actual registry or scientific journal.

## Decision

**Qualified software-mechanics pass.** I found no blocker in the compiled preparation/application separation, explicit retry/resume lineage, or CAS/journal handoff for the stated scope. The six author tests use invented temporary native evidence and do not qualify an actual count candidate. The compiled TX2026 preparation is pending data only: its owner output directory does not exist and no application recipe or real selection was created. An independently reviewed decision, successful exact native preparation, current journal proof, and the existing selection CLI's checks remain necessary before actual application.

## Specific findings

- Preparation compilation requires a pinned native spec, a fresh owner output and `application: null`; its receipt gate requires `selectionEstablished=false`, `empiricalStatus=unassessed`, and `publicationAuthorized=false`. A pending preparation cannot compile into application. Application compilation binds the same native spec, completed preparation, candidate/task SHA, decision, journal cycle, expected predecessor/revision and stable command ID. It does not substitute for native inspection or independent scientific review.
- Retry copies the prior command and input pins, changes only queue/attempt/output lineage and the explicit reason, and requires a pinned terminal with matching old specification and verified cleanup. It clears any consumed prelaunch proof. The queue/executor then check the exact previous terminal, last retained claim, process/session absence and fresh output under their existing ownership controls. A fabricated compiler-level terminal alone cannot authorize enqueue.
- Prelaunch resume keeps the same unused attempt, execution spec and output role; it accepts only pinned binding/result/release for a sealed never-launched deferral. The same-store enqueue path checks all prior references under the dispatcher lock and rejects a launched, active, quarantined or competing attempt. Restored original input bytes are required before launch. A deferred attempt has no executor terminal to treat as a launched retry.
- The existing scoped-selection CLI performs fresh native inspection, source/decision checks and journal checkpoint verification. Its registry uses `BEGIN IMMEDIATE` and rechecks CAS inside the transaction. An exact command replay verifies the original payload and returns `already_applied` without another event. A stale competing command fails. The attached journal is read-only and checked in the transaction; this compiler does not write it.
- Focused compile-only independent probes passed: preparation created a plan/receipt but no owner output; pinned native-spec drift was rejected; a pending preparation was rejected for application; no synthetic registry/journal directory was created. No real journal or registry was accessed. All ten author-pinned source files still match their verification hashes.

## Limits

The retry and resume compilation methods authenticate supplied evidence but do not prove current store ownership until enqueue. The author tests provide synthetic mechanics evidence for that handoff, not an actual native run. A failed application can leave a fresh partial output directory and staged immutable registry objects before the event transaction; the event/CAS guarantee is exactly-once selection, not an assertion of zero filesystem side effects. Preserve the existing manual inspection of terminal/cleanup and the required fresh output directory on explicit retry. Queue `accepted_execution` and worker `finished` remain process observations with `unassessed` qualification. No scheduler or publication authorization is added.
