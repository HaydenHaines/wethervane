Runnable/active frontier research — new opt-in domain, not production integration

The prior source-bound incremental derivative removed full external-history authentication from ordinary operations under an explicit trusted mutable-store contract, but still scanned historical owners/reservations to find candidates and capacity. This separately versioned implementation removes those selection scans. Frozen queue-v2, admission core, executor, prior derivatives and other sessions' files are unchanged. No models or scientific outputs ran. Independent review remains required.

What is implemented

A fresh domain has a distinct config and database meta version, so the old admission core's opened/admit rejects it rather than allowing admissions without the frontier. initialize leaves interrupted bootstrap visible and does not adopt a partial root. Source identity covers the actual loaded dispatcher/admission core and unchanged V2 validator/executor/ledger/receipt modules and exact paths. Bare SQLite and cooperating writers remain trusted.

pending stores only unreserved admitted jobs, with a stable autoincrement admission/job ordering, unique attempt, nonnegative unresolved-producer count and optional failed-producer block marker. A partial ready_frontier(seq,attempt) index contains only remaining=0 and blocked IS NULL rows. dependency_edges uniquely stores each producer/consumer pair; multiple dependency roles from one producer contribute one unresolved producer. The reverse index serves explicit audit. active has one slot, constrained slot=1 with a unique reservation FK; capacity is structurally one. Immutable owners/reservations/releases and all admitted canonical plan bytes remain preserved.

Admission validates the supplied complete plan/current input and executable pins with unchanged V2 validators, preserves fresh canonical/nonoverlapping output and predecessor/retry semantics and atomically inserts evidence, ownership claims, dependency edges and all pending rows in one BEGIN IMMEDIATE transaction. A precommit process death rolls back every projection; a postcommit retry retains the same claims/frontier. There is no separately committed admission-to-frontier replay gap. Exact admission retry retains the inherited fresh-output restriction: it is supported before an output path is created, not a new postexecution retry API.

Reservation publishes the exact binding scaffold as before, then atomically inserts the immutable reservation and active slot and removes the pending row. A precommit crash leaves it runnable; a postcommit crash retains capacity and the reservation for the unchanged executor's recovery path. At release, exact result/release/terminal/output pins and cleanup are authenticated first; immutable release insertion, dependent-count decrement or failure block, and deletion of the active slot commit together. Unique release identity plus active ownership prevent a second committed decrement. Precommit crash leaves capacity and old counts intact; replay is exact; postcommit crash retains the completed transition.

An ordinary idle tick selects active directly from its at-most-one row and at most one ready candidate from the partial index. It never enumerates owners, historical reservations/releases or all pending rows. Cached readiness is selection only: full selected dependency ancestors, current result/release/terminal/output pins and executor state are still authenticated synchronously by unchanged binding/reserved_binding/observed_result/verified_release/reconcile logic. The selected chain is checked again after prepare immediately before launch. A corrupt readiness hint or changed selected producer output fails closed and does not authorize a consumer. Active unknown/live/cleanup-unverified states retain capacity. This code does not claim arbitrary old unselected-history bytes are rechecked each idle tick.

Failure lifecycle is deliberately incomplete

A failed producer directly marks immediate pending consumers blocked, retaining their unresolved count. It does not recursively mark grandchildren: those remain pending/waiting with blocked=None and remaining>0 because their direct producer never executes/releases. They cannot become runnable under the authorized transitions. A tested three-level failure leaves middle blocked and last waiting; no downstream command launches. There is no cancellation, block-propagation service, deadlock resolution or queue-completion detector. reserved=0 means free capacity only, and every operational observation says queue_completion=not_inferred_from_empty_frontier. Pending/blocked rows may remain indefinitely until a future explicitly designed lifecycle policy; do not report them as successful, complete or scientifically unnecessary.

Real SQLite client processes exit immediately at evidence insertion, owner insertion, frontier insertion and postcommit admission. Separate real process deaths cover binding publication, in-transaction frontier reservation, committed reservation, executor prepare, real launch, result publication, release publication, in-transaction release insertion/frontier update and postcommit release. Replay yields one producer/consumer execution and correct ready count. Process death tests exercise SQLite rollback-journal/FULL-sync recovery after os._exit, not kernel/power-loss durability or storage corruption.

Concurrent competing plans get one retained owner and one rejection. Concurrent ticks with one owner launch exactly once; concurrent ticks with two ready owners retain at most one active slot and execute each exactly once. Other tests cover failed producer exclusion, grandchildren waiting, selected dependency-result tamper blocking, wrong database domain and a corrupted remaining count rejected by explicit projection audit and fail-closed dispatch. These are genuine invented executor commands; no fake successful scientific outcomes are supplied. Separate temporary domains execute eight tiny commands in the final eight-test suite (two chain, two independent capacity, one duplicate-owner, two failure producers, one tamper producer).

An explicit audit_frontier(db) reconstructs owner and unique-edge projections from canonical admitted plan evidence, checks disjoint output ownership, active=reservations−releases, pending=owners−reservations, remaining counts and direct failure flags. This audit intentionally costs O(history+graph) and reads stored result declarations; it is structural and does not independently authenticate all external historical scientific inputs/outputs. It is not an automatic idle-tick scan, protected archive head or repair service. Operators must not confuse this with a full executor/history audit or rollback protection.

Remaining before adoption

Independent source/failure review and a real durable-service/lifecycle contract are required. This is a new store, not a V2 migration. No protected immutable archive head or arbitrary historical mutable-file tamper gate exists. Database owner can drop triggers/coherently rewrite or roll back projections; unvisited released history cannot be authenticated without reading it or changing storage guarantees. Current source locks coordinate this dispatcher only; foreign/raw SQLite writers are not supported. Disk-full/fsync uncertainty, actual OS power loss, controller cleanup/supervisor edge cases, portable backup/restore and all prior executor trust boundaries need separate review and stress testing. Schema constraints prevent authorized transition mistakes, not malicious same-user filesystem tampering.

No unattended daemon, cancellation, descendant block propagation, failed-bootstrap repair, cross-plan dependency authority, prelaunch new-plan resumption, source admission/promotion or scientific qualification is implemented. No fully authenticated thousands-cycle benchmark or multibranch/large-DAG correctness/scale campaign is claimed. The inherited recursive selected-dependency verification and source hashing remain expensive by design until a stronger immutable/audit boundary is chosen. Keep released history for ownership/provenance; only its routine runnable/active selection scan is removed.
