## How a cycle advances

1. **Diagnose:** bind the full incumbent configuration, target, scope and cutoff. Inspect actual errors and fitted ablations. If evidence cannot rank layers, record that and pursue the missing evidence rather than inventing a rank.
2. **Research:** reuse the backlog, search primary sources and ask complementary Luna/Sol agents to challenge mechanisms, overlap, identification, data availability and implementation. Finish with a falsifiable hypothesis and the smallest useful alternative.
3. **Plan:** freeze a versioned comparison specification before its runs. Record inputs, source release dates, target labels, configuration/source hashes, race set, horizons, tuning opportunities, numerical tolerances, proper scores and material-regression guards. Amend with a new version and reason when needed.
4. **Develop:** preserve incumbent code and outputs. Replace one component definition; jointly refit all affected parameters. Changes in data, likelihood or scientific target are explicit experimental arms, not hidden benefits.
5. **Evaluate:** execute and preserve numerical diagnostics, predictions and paired scores. Record failures as failures. A wrapper timeout is not proof its child exited: verify process termination before retrying or writing into a new run directory.
6. **Review:** an independent reviewer checks implementation, artifacts, scope, information matching, simulation uncertainty and the conclusion. A recorded approval is a traceable review result, not an automated substitute for this work.
7. **Decide:** promote, retain, reject, narrow scope or gather more evidence. Preserve every version and reason. Inconclusive evidence retains the incumbent. Promotion updates a scoped full-configuration reference atomically and keeps the previous reference available for rollback.
8. **Publish:** after a qualified owner export exists, bind the frontend to exact results, test saved configurations/comparisons/maps/scores and deploy within the user's standing authorization. Never redirect an old saved configuration to new scientific bytes. Publish capability and experimental/testing status separately.
9. **Repeat:** recompute the diagnostic priority list and start the next cycle. Archive enough state to resume after interruption. Do not repeat an identical negative experiment without new information, a corrected implementation or an explicit sensitivity question.

## Complementarity audit

First establish coherent quantities and likelihood ownership: residents, citizen exposure, legal eligibility, registration, respondents, participants and candidate votes are different quantities. Shared samples and administrative totals have one owner, with dependence modeled where reused. Preserve the protected population states, original masses and separately normalized downstream laws.

Then compare full joint fits with scientifically valid replacement/ablation configurations. Removing a required count or measurement law is not a valid ablation; substitute a strong simple law with the same target/support. Hold other component **definitions** and comparison inputs fixed where possible, but refit affected parameters. Reusing frozen posterior parameters would answer a different question.

For a lower-is-better loss, a simple incremental diagnostic is `loss(full stack with simpler role) - loss(full stack)`. Positive values support the incumbent role's contribution; negative values motivate investigation. Show its uncertainty and per-cycle behavior. This is conditional on the rest of the stack, not an intrinsic universal score for that role. Pairwise replacement experiments can expose masking or duplication; interpret interaction contrasts with their uncertainty rather than demanding independent effects from dependent components.

Rank actionable weaknesses using practical predictive harm, uncertainty, reliability and available identifying evidence. Do not give a universally necessary accounting layer a poor ranking just because it cannot be switched off, or select a complex mechanism solely because its retrospective score is worst. Record the reasoning behind each selected cycle.

## Durable execution and recovery

Each cycle needs immutable input/configuration/prediction/review references, an append-only history, a current checkpoint, declared owner, attempt IDs, process receipts and retry reason. Content hashes detect changed artifacts. Record attempts separately; never overwrite evidence from a failed process. Long jobs require bounded execution and verifiable child-process cleanup. A checkpoint must say what actually finished and the exact next operation.

The initial journal is local bookkeeping. Connecting scientific runners, worker recovery, reviewed promotion and deployment remains explicit work. Thousands of journal entries are not thousands of executed or qualified model comparisons. A standing Codex goal continues while the session is running; an unattended service requires its own real scheduler and monitoring.

## Using the initial journal

`ledger.py` uses Python's standard library and local SQLite. Artifacts are copied under their SHA256 names; journal writes use transactions, command IDs and expected revisions. A retry with the same command ID and payload returns the previous receipt. A changed payload with that ID is rejected. Failure checkpoints retain their phase. Recommendations, including `promote`, only record decisions; they cannot activate a model.

The working store is `.improvement-ledger/` at this worktree's root, excluded from Git. The bootstrap records the inventory/research checkpoint, not a competing-model result. The checked-in binding and export make that scope explicit. After creating the initial checkpoint, inspect it from the repository root with:

```sh
python3 -B research/improvement-loop-20261024/ledger.py --root .improvement-ledger status bootstrap-20261024
python3 -B research/improvement-loop-20261024/ledger.py --root .improvement-ledger export bootstrap-20261024
python3 -B -m unittest discover -s research/improvement-loop-20261024 -p test_ledger.py -v
```

`create`, `artifact` and `checkpoint` subcommands expose the recording API; each has `--help`. Create a new cycle when the bound hypothesis, target or incumbent changes. A `planned` or `reviewing` label is user-supplied bookkeeping, not proof that all scientific requirements have been satisfied. Keep source/prediction bundles in durable owner storage and link exact hashes through versioned manifests. The local database and artifact directory need to be backed up together; the journal does not supply a backup service.
