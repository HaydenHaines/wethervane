# Finite queue with owned executor — research V1

A **new self-contained successor**, frozen for independent review once evidence pins are recorded. No old queue, store, packet or owner job was changed. No production adoption, model execution, forecast qualification or thousands-cycle claim. All workflow scientific qualifications remain `unassessed`.

This implements the source requirements in `../queue-executor-integration-design-sol-v1` and its independent Luna review. Source ancestry: finite-run queue V2, reviewed direct-executor ownership V1, and reviewed nonce-based receipt projection V2. Exact inputs and final code/tests are pinned in evidence.json. `FAILURES.md` records genuine bugs, inherited API differences and preserved failed runs.

## Implemented contract

The queue has distinct `LocalExperimentQueueStoreFiniteOwnedResearchV1`, lifecycle, creation-marker and final schemas; executor stores/intents/preparations have distinct integrated schemas. Exact absolute module paths, source hashes and roots are checked. No old store adoption or migration. Module imports from another source directory are rejected. The copied queue retains canonical ADMITTING → ACCEPTED intake, same-lock sealing, post-seal exact interrupted admission repair, no dispatch while ADMITTING, original dependency/result/release integrity, explicit empty policy and terminal-failure disposition. Controller executions remain in separate standalone roots.

Historical ownership validation now checks immutable-by-convention spec shape/lexical identity and exact source/store/intent/claim bindings without requiring all old runnable inputs to remain live. Runnable target specs still receive the original current executable/cwd/input/canonical-namespace checks at admission, prepare, launch, supervisor and child. Ownership audit separately reports current historical runnable-input drift; it does not silently call old inputs clean or block an unrelated preparation solely for that drift. The inherited independent-source regression passes. Dependency byte drift and terminal/output corruption retain their original fail-closed consequences. Generated forecast/science validation is not supplied.

An execution-domain marker binds queue store pin, execution root and dispatcher lock inode/device. Managed prepare and launch require a held dispatcher flock open-file description **and** a matching unreleased reservation/pinned effective binding. They also re-read the source-bound lifecycle in read-only mode: all admissions must be ACCEPTED with exact plan/receipt/scaffold pins and valid sealed digest. FINALIZED cannot start new work. Bare lock-file opening, absent reservation, corrupted admission/marker, marker root mismatch and symlinked managed root do not authorize a launch. A marker for a different standalone child root does not claim that standalone domain.

This is a local cooperating-manager gate, not cryptographic caller authentication or protection against same-user code rewriting files, invoking legacy code or forging the whole local store. Managers possessing the dispatcher lock and valid reservation can use the guarded entry points; the gate checks evidence, not a Python caller's identity. Direct standalone clients use their own domains. Cross-root output isolation and OS write sandboxing are not provided. Explicit operator stop/recovery remains governed by original process identity/job-lock rules; these cannot authorize an additional launch or release queue capacity by themselves.

Executor preparation serializes subtree claims with its ownership lock and retains the original nonblocking job lock. Durable source-bound intent precedes attempt/scaffold files. Exact matching replay repairs interrupted publication; it does not overwrite drift or adopt launched partial scaffolding. Completion creates queue ownership acknowledgment pins before dispatch/launch. Acknowledgments bind exact queue binding/reservation plus executor intent/prepared pins. The effective dependency-substituted spec is used throughout; unbound SHA sentinels are not executable intent specs.

Supported process-death phases and ordinary publication errors keep the queue reservation. Transient lock contention/I/O publication failure is pending rather than a false terminal or automatic release. Known target live-input/fresh-output rejection before intent is the original explicit never-launched deferral. Corruption remains retained/quarantined; an unexpected partial output is not guessed safe. Exact existing-record publication retry compares content and re-fsyncs file plus parent. A returned success still assumes successful underlying filesystem semantics; unresolved errors propagate or remain pending. There is no universal fsync-uncertainty certification.

Ownership revalidation now occurs before terminal queue release, for already released results, and before final DB commit. It cross-checks the executor intent roster against queue reservations and **effective** bindings, verifies store/intent/prepared/job/output claims and ownership acknowledgments, and rejects unknown external attempts. Post-release corruption cannot be hidden by cached queue success. Final evidence includes ownership domain/store/intents/spec/prepared/job/output claims and queue acknowledgment pins as well as original terminal/dependency/output evidence. Historical drift is included in the final observation. Repeated finalization must revalidate and reproduce exact DB bytes; projection remains exclusive, nonce-based and fsynced. Existing final receipts are not overwritten after later drift.

No execution store is required for an explicitly empty or never-prepared run. A previously acknowledged execution store/intent cannot vanish and be treated as empty. Before acknowledgment, the independent queue accepted plan/binding/reservation continues to reserve its identities; it is not an external immutable witness.

## Lock order and bounds

D = dispatcher flock, S = intake SQLite transaction, O = executor ownership flock, J = nonblocking job flock.

- Enqueue/seal use D → S; real admission files are created after committing/closing S and ACCEPTED is recorded in a later S under D. Read-only admission preflight does not prepare executions.
- Managed preparation/launch gate performs D → bounded read-only S, closes S, then preparation takes D → O → J(nonblocking). O and the manager's J close before launch. Launch takes D → J, inherited by worker.
- Ownership audit takes D → O and releases O before final D → S commit/projection. It does not wait for worker completion. Supervisor/child load does not acquire D/O; no J → D callback is introduced.

D/O acquisition polls nonblocking flock for at most a requested 0.5 s; intake SQLite and managed read-only admission use a 0.5 s busy timeout. Timeout is not an integrity verdict or capacity release. These are per-acquisition bounds, not a hard deadline for an entire tick: multiple audits, scheduler delays, hashing, directory scans and filesystem calls can still take longer. No real-time/I/O-hang guarantee. Unknown/live/corrupt reservations remain fail closed. Worker errors can terminate a controller; another caller must resume the store. This is not a resilient deployed service.

## Tests and exact scope

Run `sh run_tests.sh` at nice15. **73 tests passed in 76.129 s** in tests-final.log: 32 successor queue cases, 14 finite-intake, 12 direct-executor and 15 integration cases. Cleanup verified 123 recorded fixture identity observations, with direct tests asserting their own cleanup. The suite includes all 32 original queue scenarios through an explicit successor class (29 unchanged methods, three named finite-intake API substitutions), all 14 finite-intake tests, all 12 direct-executor tests and the new actual integration cases. The untouched original full run has documented failures; see FAILURES.md rather than interpreting substitutions as a claim of unchanged API compatibility.

New cases exercise actual tiny Python processes: nine preparation/ack/dispatch death boundaries and exact reservation replay with one launch; post-publication OSError pending/retry; released ownership mutations independently checked before sticky quarantine; final effective-spec/ack pins; post-final mutation preserving receipt; naked or unreserved direct managers; accepted-admission drift despite held D; bounded D/O/SQLite contention; historical drift with unrelated work plus final reporting; unknown claims, missing/mismatched markers, managed root alias, unrelated standalone marker and publication re-sync. Fixture processes have no scientific work. Authenticated pidfd cleanup waits until recorded fixture identities are not alive; direct tests separately assert their cleanup. A narrow post-run process snapshot supplements, rather than replaces, those checks. Temporary stores are removed.

The standalone suite deliberately preserves its **negative** test: external deletion of the sole pre-scaffold intent without another witness can free that standalone claim. Process death alone does not delete the fsynced intent. Local owner writes, coherent rollback or deletion of all witnesses remain outside the guarantee. No hostile-owner or immutable-public-ledger claim follows from the queue's additional local evidence.

## Remaining limits

Reliable local Linux flock, SQLite/FULL, hard-link publication, file/directory fsync and cooperating source-bound clients are assumed. No NFS, real power-loss, disk-full, storage-controller failure, exhaustive schedule or noncooperating legacy-manager proof. Symlink checks close the tested managed-root downgrade, not arbitrary namespace TOCTOU between validation and child writes. Fresh interpreter/dependency pins do not sandbox code.

The ownership registry and SQLite are owner-writable. Claim files are exclusively published but not WORM. The new gate is not an independent hostile-user security boundary. Controller death recovery is tested only in bounded invented fixtures; production operation, cancellation, garbage collection, migration, fairness and long-term disk handling are absent.

Repeated full ownership audits include pairwise history scans and live pin reads. With a released-result audit per job, worst-case tick work can be cubic in retained claim count before byte-hashing costs; this is a source-derived concern, not a measured scaling result. No incremental/scaling improvement is claimed. Peak CPU/RSS/temporary disk was not measured. Test elapsed time is not a thousands-cycle benchmark. Independent review and a fresh source/resource boundary are required before any later integration or workload; no extra user-approval gate is introduced.
