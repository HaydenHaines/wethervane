## Conditional shares: safe current presentation, remaining boundary notes

`lib/house-polling-shares.ts:68–250` checks the separate conditional-share schema, source/audit pins, historical experimental mode, complete coverage ledger, D/R pair summaries, polling coverage and disabled full-chamber/proof capabilities. It retains raw source fields, including generic `outcomes.winProbability`; those represent the **conditional pair**, not the ultimate group-winner target. The backend metadata explicitly says so.

The current production caller uses the stronger combined boundary: `lib/house-reviewed-client.ts:13–25` checks the exact entry, source-byte hash and canonical share-content digest. `components/HousePollingShares.tsx` renders **share means/intervals only** and states these are not district winning chances; it does not display the generic conditional `winProbability`, score it as an ultimate winner, or supply chamber control. `HouseGroupResults.tsx:126` keys that component by entry ID, preventing the otherwise possible cached-share result from surviving a model/year change. The source winner/group forecast remains in the separate group panel.

Do not route this packet through the generic legacy candidate-probability/actual-winner screen without retaining its conditioning boundary. The structural share parser alone is not a replacement for the exact publication/client digest check. Its optional raw `jointDraws`/summary fields are not a new full-chamber capability, and a conditional D/R threshold crossing must not become a district/group winner assertion.

Two smaller follow-ups, reported to Sol:

Still, a fail-closed API consistency test should either reject contradictory redundant summaries or document them as ignored derived fields. Likewise `nativeMetrics` forwards the native metrics object (including explicitly failed seat-mean precision metadata) for round-trip validation; UI consumers must use the bounded race summaries, not promote those research diagnostics into chamber output.
