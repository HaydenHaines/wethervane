## Contract and integration

One immutable store represents one finite generation. `initialize` creates a source-bound store and FULL-synchronous SQLite lifecycle plus a durable creation marker. The marker prevents accidental missing-DB reset even when a committed intent has not created any queue files. Interrupted initial setup can be retried; deletion of both marker and DB by an owner is outside this trust boundary.

All enqueue, seal, tick, status and finalize entry points validate source identity and use **the same original `dispatcher.lock` flock**. SQLite BEGIN IMMEDIATE transactions are nested inside that lock, never a replacement independent lock. `_enqueue_locked` and `_tick_locked` are the original logic with their outer lock removed; wrappers own the lock for the complete operation. No alternate controller should call these internal functions or write into the execution substore.

OPEN accepts new plans. Read-only original admission checks precede insertion of a canonical ADMITTING intent. That intent commits before any real queue file is created, retaining attempt/output claims through caller death. New competing intents are checked against pending claims; accepted claims and explicit prelaunch resumptions retain original V3 checks. ADMITTING→ACCEPTED commits only after original plan/admission publication and exact job directories exist. Exact same-plan enqueue repairs an interrupted admission even after sealing. Changed duplicate IDs and new post-seal IDs are rejected without admission. Accepted exact retries are idempotent.

`seal --allow-empty` (or `seal` without the explicit empty policy) commits SEALED plus a digest of the complete intent set under that same dispatcher lock/transaction. A genuine enqueue either commits its intent before sealing or is rejected afterward. Empty without the explicit empty policy cannot finalize. Pending ADMITTING intents may be sealed but **block all dispatch/reconciliation until exact repair**. This conservative global stop prevents a published admission receipt from launching before ACCEPTED; it can delay unrelated work.

`finalize` first requires the complete accepted frontier, then runs the original full tick/release/dependency reconciliation under the lock. It can launch ready work and reject finality as pending; it is not a read-only command. Finality requires no reservations, unknown reservations, partial or quarantined admissions and terminal recorded outcomes for every admitted job. Unknown exit is a recorded failure only after original executor recovery has proved cleanup; a live/unknown reservation is retained. Terminal failures and blocked descendants produce `terminal_with_failures`, never success. OPEN is idle, never finalized.

The canonical final document pins admissions, bindings, reservations, results, releases, executor terminals and selected output receipts, with the full reconciled observation. Its exact bytes and FINALIZED state commit atomically in SQLite. Projection uses fresh nonce exclusive temporary files, file fsync, exclusive hard-link publication, directory fsync, cleanup and directory fsync. Repeating finalize revalidates original evidence and requires identical DB final bytes before repairing/returning projection; conflicting files are never overwritten. Publication errors leave recoverable nonce temp files. A missing final receipt does not undo FINALIZED. Corruption does not authorize a new final receipt. `status` is explicitly a metadata observation, not finality authentication; `work` waits for seal and distinguishes idle OPEN from finalized.

## Limits and next gates

This remains an owner-writable SQLite index. Accidental partial writes/process crashes are different from a malicious owner rewriting DB, marker and files coherently. No external append-only witness, cryptographic controller authorization, anti-rollback hardware or hostile writer exclusion is provided. Original historical file verification remains in the copied reconciliation paths; no claim of detecting arbitrary coherent DB/index rewrites is made. All callers must cooperate with flock. Ordinary local SQLite/FULL/fsync/hard-link semantics and a reliable filesystem are assumed; no NFS, disk-full matrix, filesystem fault injection, fsync ambiguity certification or real power-loss testing was performed.

Remaining coverage includes initial-setup crash positions, native mixed-import/schema rejection subprocess matrix, all inherited regression cases adapted to successor semantics, exhaustive enqueue/seal/finalize schedules and long histories. No incremental index or complexity improvement is introduced; full-history scans remain. There is no cancellation/removal/reopening of a committed intent or sealed generation: unrecoverable corruption blocks that generation for explicit investigation. No automatic repair of arbitrary damaged accepted evidence is attempted. The conservative ADMITTING stop, operational errors and worker error receipts need further service-level design. Source tests demonstrate bounded cases, not universal correctness.

Independent review should challenge lock ordering, pre-file claims, accepted/prelaunch-resume distinctions, all original integrity paths, final evidence completeness and DB/projection recovery before any adoption. No additional user approval gate is introduced; technical review and fresh resource boundaries remain necessary for any later work.
